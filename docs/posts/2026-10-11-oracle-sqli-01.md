## 요약

첨부해두었던 SQL Injection 실습 정리 노트의 **문제 1**을 블로그 양식으로 옮긴 기록이다. 원본에 적힌 풀이와 입력값은 그대로 남기고, 쿼리와 중요한 부분을 읽기 쉽게 구분했다.

| 항목 | 내용 |
| --- | --- |
| 문제 | 문제 1. 로그인 우회 |
| 대상 계정 | `z_answer@eqst2.com` |
| 풀이 상태 | 해결 — 원본 노트에 기록된 상태 |
| 조건 | 필터링 없음 / AND·OR 자유롭게 사용 가능 |
| 핵심 개념 | AND가 OR보다 먼저 묶이는 연산자 우선순위 |
| 쿼리 구조 | 추정 |

!!! note "기록의 범위"

    이 글은 워게임 실습 노트의 1번 문제를 옮긴 내용이다.
    쿼리 구조는 원본에서도 **추정**으로 표시되어 있으며, 이 글을 작성하면서 로그인 동작을 다시 검증한 것은 아니다.

## 입력값과 고정값 구분

아래 쿼리는 SQL 문법 종류가 아니라 **문자가 어디에서 왔는지**를 기준으로 색을 나눈다. 작은따옴표와 연산자도 예외 없이 같은 기준을 적용한다.

| 구분 | 의미 |
| --- | --- |
| <span class="sql-fixed">초록색 · 고정값</span> | 개발자가 미리 작성한 쿼리 틀과 작은따옴표 |
| <span class="sql-input">파란색 · 입력값</span> | 내가 입력한 모든 문자: 이메일, 비밀번호, 연산자, 작은따옴표 |

**완성된 쿼리의 문자는 초록색 또는 파란색 중 하나로 표시한다.** 특히 내가 입력한 `OR`와 작은따옴표는 SQL 문법으로 해석되더라도 파란색이다.

## 쿼리 구조 — 추정

<div class="highlight sql-origin"><pre><code><span class="sql-fixed">WHERE email = '</span><span class="sql-input">조건1</span><span class="sql-fixed">' AND password = '</span><span class="sql-input">조건3</span><span class="sql-fixed">'</span></code></pre></div>

`조건1`과 `조건3`은 각각 이메일과 비밀번호 입력값이 들어가는 위치를 나타낸다.

## 사고 흐름

다음은 원본 노트의 사고 흐름이다.

1. 비밀번호 공격포인트(조건3)는 모르니까 항상 **거짓**으로 고정됨
2. `조건2 AND 조건3` → 거짓과 AND로 묶이면 조건2가 뭐든 **무조건 거짓**
3. 따라서 `조건1 OR (조건2 AND 조건3)` 구조로 만들면, 전체 결과는 **조건1에만 좌우됨**
4. 조건1 = `email = '실제 이메일'` → 진짜 이메일을 알고 있으니 **항상 참**
5. 결론: 조건1과 조건2를 **OR**로 엮기만 하면 됨, 조건2 안의 내용은 문법만 맞으면 뭐든 상관없음

!!! info "원본 표현을 읽을 때의 전제"

    위의 “항상 거짓”은 **입력한 임의의 비밀번호가 해당 행의 실제 비밀번호와 다르다**는 전제다. 비밀번호를 모른다는 사실 자체가 비교 결과를 거짓으로 만드는 것은 아니다.

    “항상 참” 역시 **이메일이 일치하는 대상 계정의 행에서 참**이라는 뜻이다. 다른 계정의 행에서는 이메일 비교가 거짓일 수 있다.

## 적용 페이로드

### 이메일 입력칸 — 공격포인트

아래 문자열 전체를 이메일 입력칸에 넣는다. 끝의 작은따옴표를 임의로 추가하지 않는다. 뒤쪽 따옴표는 원래 쿼리 틀에 남아 있는 문자를 사용한다.

<div class="highlight sql-origin"><pre><code><span class="sql-input">z_answer@eqst2.com' OR '1'='1</span></code></pre></div>

### 비밀번호 입력칸 — 공격포인트

원본에서는 아래 임의의 값을 사용했다.

<div class="highlight sql-origin"><pre><code><span class="sql-input">asdf</span></code></pre></div>

## 완성되는 쿼리

원본 노트에 정리한 완성 쿼리는 다음과 같다.

<div class="highlight sql-origin"><pre><code><span class="sql-fixed">WHERE email = '</span><span class="sql-input">z_answer@eqst2.com' OR '1'='1</span><span class="sql-fixed">' AND password = '</span><span class="sql-input">asdf</span><span class="sql-fixed">'</span></code></pre></div>

### 작은따옴표 8개의 출처

완성된 쿼리를 왼쪽부터 읽으면 작은따옴표는 총 **8개**다. 초록색 따옴표는 원래 틀에 있던 문자이고, 파란색 따옴표 4개는 이메일 입력값에 직접 넣은 문자다.

| 순서 | 위치와 역할 | 출처 |
| --- | --- | --- |
| 1 | 이메일 앞: 문자열 시작 | <span class="sql-fixed">개발자</span> |
| 2 | 이메일 뒤: 이메일 문자열 닫기 | <span class="sql-input">내 입력</span> |
| 3 | 첫 번째 1 앞 | <span class="sql-input">내 입력</span> |
| 4 | 첫 번째 1 뒤 | <span class="sql-input">내 입력</span> |
| 5 | 두 번째 1 앞 | <span class="sql-input">내 입력</span> |
| 6 | 두 번째 1 뒤: 원래 이메일 끝에 있던 따옴표 | <span class="sql-fixed">개발자</span> |
| 7 | 비밀번호 asdf 앞 | <span class="sql-fixed">개발자</span> |
| 8 | 비밀번호 asdf 뒤 | <span class="sql-fixed">개발자</span> |

!!! tip "문자 출처와 실행될 때의 역할은 다르다"

    **6번 따옴표는 개발자가 이메일 입력값 뒤에 붙이도록 작성한 문자**다. 주입 후에는 두 번째 1의 문자열을 닫는 역할을 하지만, 출처는 바뀌지 않으므로 초록색이다. 비밀번호 asdf는 내가 입력했으므로 파란색이고, 그 양옆 따옴표는 개발자가 작성했으므로 초록색이다.


### 우선순위를 괄호로 풀어보기

`AND`가 `OR`보다 우선하므로, 위 조건은 **조건1 OR (조건2 AND 조건3)**으로 묶인다. 여기서 괄호는 이해를 돕기 위한 표기이며, 실제 입력값이나 원래 쿼리에 포함된 문자가 아니다.

- **조건1:** 이메일 일치 여부
- **조건2:** 두 문자열 1의 비교
- **조건3:** 비밀번호 일치 여부

대상 계정의 행에서 이메일 비교가 참이면, 뒤의 비밀번호 조건이 거짓이어도 전체 조건은 참이 된다.

| 대상 행의 조건 | 결과 |
| --- | --- |
| <code><span class="sql-fixed">email = '</span><span class="sql-input">z_answer@eqst2.com'</span></code> | 해당 이메일의 행에서 참 |
| <code><span class="sql-input">'1'='1</span><span class="sql-fixed">'</span></code> | 참 |
| <code><span class="sql-fixed">password = '</span><span class="sql-input">asdf</span><span class="sql-fixed">'</span></code> | 실제 비밀번호가 다르다는 전제에서 거짓 |
| 전체 조건 | `참 OR (참 AND 거짓)` → 참 |

## 주의점 / 막혔던 부분

!!! warning "아무 문자열이나 넣으면 안 됨"

    공격포인트 안에 아무 문자나 넣으면 안 됨 → 문법적으로 유효한 비교식이어야 함. 예: `'1'='1'`.

!!! danger "의도와 다른 계정이 선택될 수 있음"

    연산자 우선순위(AND가 OR보다 먼저 묶임)를 모르고 OR만 쓰면 의도와 다른 행(다른 계정)으로 로그인될 수 있음.

이 풀이에서도 다른 행의 비밀번호 비교까지 참이 된다면 그 행이 추가로 조회될 수 있다. 실제 로그인 계정의 선택 방식은 애플리케이션이 조회 결과를 어떻게 처리하는지에 따라 달라진다.

## 정리

이번 문제의 핵심은 **OR을 넣었다는 사실보다, 완성된 WHERE 조건이 어떤 순서로 묶이는지 이해하는 것**이었다.

입력칸에 적은 문자열만 보지 말고, 앞뒤의 고정 쿼리와 합쳐진 최종 형태를 적어보면 작은따옴표와 연산자 우선순위를 확인하기 쉽다.
